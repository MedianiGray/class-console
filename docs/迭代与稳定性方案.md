# 迭代与稳定性方案

本方案参考成熟软件的通行做法，结合本项目"单机离线、单人开发、先本地后联网"的实际情况，定一套轻量但可持续的迭代与保障机制。目标是：每一步都能稳得住、出问题能回退、改动可追溯、下一轮有依据。

## 一、成熟软件通常怎么做迭代

对照行业通行实践，本项目采纳其中适合单机工具软件的部分：

1. **语义化版本号**：用 MAJOR.MINOR.PATCH 三段编号，让人一眼看出这次改动有多大——
   - 不兼容改动升 MAJOR；兼容的新功能升 MINOR；缺陷修复和稳定性加固升 PATCH。
2. **小步快跑、分阶段验收**：改动先在本机自测，再小范围给老师/同学试用，收集反馈后再固化；不一次性堆大功能。
3. **回归测试防退化**：每次改动后跑一遍固定的核心流程，确保新改动没把旧功能弄坏；问题用例固化成自检脚本，反复可跑。
4. **数据可备份、可恢复、可回滚**：用户数据定期导出；关键写入走事务；出问题能退回上一版程序或上一份数据。
5. **异常留痕**：未捕获错误写入本地日志，出问题后能凭日志定位，而不是只看到"闪退了"。
6. **反馈闭环**：真实使用中遇到的报错、卡顿、别扭点，记录下来排进下一轮，而不是凭感觉加功能。

> 说明：云端软件常见的灰度放量、自动灰度回滚、错误率监控大盘等，依赖服务器和多用户环境；本项目当前是单机离线，暂不引入，等阶段二接平台时再按需补。

## 二、本项目版本规则

- 版本号在 `version.py` 维护，遵循语义化版本：
  - **PATCH**：修 bug、加固异常兜底、调整细节手感（如 0.1.0 → 0.1.1）。
  - **MINOR**：向后兼容的新功能或体验改进（如 0.1.1 → 0.2.0）。
  - **MAJOR**：不兼容改动，例如换界面框架、改数据库结构导致旧备份无法读取（如 0.2.0 → 1.0.0）。
- 每发一版，在 `CHANGELOG.md` 追加：版本号、日期、新增/修复/已知边界。
- 交付给老师的压缩包或 exe，文件名或窗口标题带上版本号，便于确认拿到的是哪一版。

## 三、稳定性保障措施

### 已落地（当前版本）

| 措施 | 位置 / 说明 |
|---|---|
| 字段兜底 | 台账、日志、详情读取全部 `.get` 取值，脏记录缺字段显示空，不崩 |
| 写操作异常捕获 | 提交、归档、驳回、导入失败给出明确提示，保留已填内容 |
| 事务与回滚 | 导入备份失败时回滚，不留半成品；数据库连接异常路径也关闭 |
| 日志失败容错 | 材料操作成功后，日志写不进去不回滚、不阻断主流程 |
| 异常落盘 | 未捕获异常写入本机 `crash.log`（时间、类型、堆栈） |
| 启动自愈 | 数据库文件损坏时隔离为 `console.corrupt-时间戳.db`，重建空库后可启动 |
| 启动兜底 | 初始化失败弹明确提示，不裸 traceback 闪退 |
| 数据导出 | 材料与日志可导出 JSON 备份，随时可恢复 |
| 源码可回退 | `_backup/` 保留改动前版本；问题版本可整体退回 |
| 回归自检 | `tests/` 下保留数据层自检与 GUI 冒烟脚本，可重复运行 |

### 后续逐步补（按优先级）

- **自动备份**：每次退出或每天首次启动，自动在本机留一份带时间戳的备份，避免只靠手动导出。
- **完整性校验**：备份文件加校验信息，导入前先检查结构和字段完整性。
- **写入前校验增强**：学号与姓名对应、重复提交提示、文件名规范检查。
- **长时间运行观察**：连续使用、多记录滚动下的内存与响应表现，实机观察后再优化。

## 四、每轮迭代流程

每做一轮改动，按固定顺序走：

1. **明确改动范围**：这一轮修什么、不加什么，先写清边界。
2. **改代码**：小步改动，不动已验证通过的核心流程。
3. **跑自检**：
   - 数据层：`py -3.14 tests/selftest.py`
   - 界面：`py -3.14 tests/gui_smoke.py`
4. **本机实机走主流程**：提交 → 查看 → 归档 / 驳回 → 看日志 → 导出 / 导入备份。
5. **清理测试残留**：临时库、临时脚本、缓存不打进交付包。
6. **更新版本号与 CHANGELOG**，打包交付。
7. **收集反馈**：老师 / 同学遇到的问题记下来，进入下一轮清单。

## 五、问题反馈怎么定位

- 程序异常退出后，先看本机日志：
  - Windows：`%APPDATA%\ClassConsole\crash.log`
- 反馈问题时尽量带上：版本号（窗口标题）、做了什么操作、填了什么内容、是否报错、报错文字。
- 能复现的问题，先记复现步骤；自检脚本覆盖不到的新场景，补成新的用例。

## 六、后续优化优先级（衔接《接入规划.md》）

1. **阶段一 · 本地打磨**：附件真实落盘、Excel/CSV 导入导出、审核备注、统计看板、校验增强、体验细节。
2. **阶段二 · 平台接入**：学校在用平台的只读同步试点，再逐步开放写入、附件存储、通知。
3. **阶段三 · AI 辅助**：从分类建议切入，验证准确率后再扩齐全度检查、重复识别、文案草稿、检索问答。
4. **阶段四 · 远期**：多人协作、手机端、学期归档包、审计导出。

## 七、当前不承诺的边界

- 单机离线版本不保证多人实时一致；多人协作需后续远程方案。
- 自动化自检覆盖代码路径和常见边界，不等于所有环境、所有数据组合都零缺陷；实机不同分辨率、字体缩放、长时间运行仍需观察。
- 附件落盘、账号登录、云端同步、AI 能力当前未实现，属于后续阶段。
