冷启动结论：台账刷新是 300 条首屏 + 按需加载，不是一次性渲染 5000 行；冷启动瓶颈是 Tk 固定开销与启动解包，不是数据库。v0.27.0 打包 3.0–4.6s，用户已明确否决“冷启动例外”，不得再写成可接受。v0.27.1 换成便携目录 + 启动占位壳后，首帧约 0.6s、已有数据进主窗口中位 2.08s、干净首次 3.9s，仍高于 1s，门禁继续保持“未达标”，下一轮压 `MainWindow` 首屏构建与建库链路。

发布后负载复测（2026-11-26，同一台 i5-8250U / 8GB）：数据层全部 86.0ms、关键词 10.2ms、类别 23.3ms、统计 6.4ms、日志 32.7ms；台账首屏 25.2ms、常驻 38.2MB；源码冷启动中位 2238.2ms、打包中位 4600.4ms。干净目录首次启动 12.2s，已有数据二次启动 4.8s。上表 59.1 / 15.6 / 3050 为更早的空载值，保留作最好情况，不覆盖本次负载值。

- 结论：启动链路从“每次解包”改为“解压一次 + 首帧占位”，同机已有数据约快 2 倍、干净首次约快 3 倍；1 秒目标仍未达成，继续迭代 `MainWindow` 首屏构建与建库。

## 五、v0.27.2 分帧启动复测（2026-11-26，Windows 11）

同一台机器、便携目录版最终包（Python 3.14 + Tk 9），`tests/perf_portable.py` 双段口径：窗口可见 = 主窗口标题不再含“正在打开”且宽度 ≥900；内容就绪 = 进程在 `CC_STARTUP_READY_FILE` 落标记（当前视图补齐完成）。

| 口径 | 窗口可见 | 内容就绪 |
| --- | --- | --- |
| 同机已有数据（5 次） | 977.5 / 977.6 / 977.8 / 1032.1 / 1080.8ms，中位 **977.8ms** | 中位 1514.9ms（1477.3–1562.3） |
| 干净目录首次 | 2466.0ms | 2969.2ms |
| 单文件版（3 次） | 2918.3 / 4403.2 / 8068.2ms，中位 4403.2ms | 中位 4908.8ms |
| 对照 v0.27.1 便携版 | 2078.1ms | 未测（当时只认“进主窗口”） |

- 结构变化：`MainWindow(staged=True)` 只建外壳与占位卡，`start_content()` 在主循环里补视图且**建完才撤占位**；看板空态懒建；类别分布与近期动态行复用；数据层与界面层导入挪到品牌加载页之后。
- 判定：**窗口可见已进入 1 秒区间，但内容就绪仍 1.5 秒，且 5 次里有 2 次窗口 1.03–1.08 秒**。门禁“启动 ≤1000ms”按单次全达标判定，因此继续记“未完全达标”，不得写成“1 秒开机”。
- 下一步：把类别分布（6 行 × 4 控件）与近期动态（4 行 × 5 控件）各合成一张 Canvas，再把顶栏 20 / 侧栏 40 控件的外壳分层；目标是把内容就绪压进 1.2 秒以内。
- 发布：tag `v0.27.2` 指向 `773c657`，Release `459497478`，资产 `796187741`（便携 zip，32,994,326 字节）/ `796193408`（单文件，32,362,641 字节），API digest 与本地 SHA256 一致；Pages 部署提交 `773c657`，线上落地页含 v0.27.2 且下载链接返回 200。
