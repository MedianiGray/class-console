# 启动性能：分帧启动改造（0.27.2 → 0.28.1 外壳三层）

状态：0.27.2 已在 Windows 打包复测；0.28.0 加入文件室批量工具后重新出包复测，窗口可见与内容就绪均比 0.27.2 慢约 0.4 秒（第四节）；**0.28.1 用外壳三层 + 包体瘦身把这 0.4 秒收回来**，便携版中位 829.0ms / 1416.8ms（第五节）。按门禁"每一次都达标"的严格口径，6 次里各有 1 次略超（1036.8ms / 1668.8ms），因此记"中位达标、个别次数未达标"，仍不写"已达标"。

> 版本号说明：本项在仓库任务里编号 #190「v0.27.3：看板控件合并与外壳分层」。0.28.0 已先发布并按语义化版本前进，版本号不倒流，实际以 **v0.28.1** 交付，内容与 #190 一致。

## 一、改了什么

1. **分帧启动（`main.py` + `ui_main.py`）**
   - `MainWindow(master, repo, staged=True)`：只建顶栏、侧栏、标题栏与状态栏，内容区先放一张占位卡（“正在载入工作台…”）。
   - 窗口按最终尺寸居中、`update` 出首帧后，用 `root.after(1, …)` 在主循环里补当前视图，不再让首帧等完整界面。
   - `start_content()` 幂等；`switch()` 在占位期被调用时先置“内容已就绪”再撤占位，中途跳转不会留下占位卡。
   - **占位卡在视图建完之后才撤**，中间不出现空白帧。
2. **看板空态按需创建（`ui_dashboard.py`）**
   - “没有材料 / 没有动态”两个空态原来启动即建（共 16 个控件），改为 `doc_empty` / `log_empty` 首次需要显示时才建。
3. **类别分布与近期动态行复用（`ui_dashboard.py`）**
   - 原来每次 `refresh()` 都 `destroy` 全部子控件重建（约 38 个控件）；改为行只建一次，刷新时只改文字、数字与横条比例。切页、入账、改状态都不再重复付构建成本。

## 五、0.28.1：外壳分三层 + 包体瘦身（2026-11-27，Windows 11）

### 1. 先拆段，再动手

0.28.0 那 6 次全部 `ok=false`，且 `prepareMs` 每次 1.6–2.4 秒（临时建库抖动），只看得见"慢"看不见"慢在哪"。所以先给自己加了一路分段 trace（`CC_STARTUP_TRACE` + `CC_STARTUP_READY_FILE`，临时 APPDATA、跑完 taskkill），从源码稳定跑两次，结构一致：

| 标记 | RUN1 | RUN2 | 该段耗时 |
| --- | --- | --- | --- |
| `main-enter` | 0 | 0 | — |
| `loading-shell-painted` | 536 | 549 | 首帧前的解释器 + Tk 热身，约 0.53s（硬底） |
| `imports-ready` | 555 | 569 | +19 |
| `repository-ready` | 566 | 580 | +11 |
| `shell-status-built` | 572 | 586 | +6 |
| **`shell-topbar-built`** | **847** | **863** | **+275 ← 单块最大** |
| `sidebar-skeleton` | 848 | 864 | +1 |
| `window-shell-built` | 925 | 938 | +77（侧栏 nav + pack） |
| **`window-shell-painted`** | **1088** | **1102** | **+163（首帧绘制）** |
| `content-start` | 1090 | 1104 | — |
| `shell-nav-built` | 1120 | 1133 | +30（推翻"侧栏 40 控件最重"） |
| **`content-ready`** | **1592** | **1648** | **+392 ← 第二块** |

三处大头：顶栏 275ms、首次绘制 163ms、内容区 392ms。侧栏 nav 只有 30ms，原来"合并看板控件"的假设方向是对的但不是主要矛盾。

### 2. 三层落地

1. **首帧只留骨架**：`_build_topbar(core=True)` 只建品牌块（logo + 「班级操作台」）后立刻返回，右侧搜索框 / 本地版标记 / Ctrl K / 设置 / 提醒 / 身份卡全部挪到 `_build_topbar_extras()`；侧栏只铺底色；内容区放一行 `_build_splash()`。顶栏从 275ms 降到 76–110ms。
2. **第二帧出主内容**：`finish_shell()` = 撤占位 → `_build_content()`（页头 + 视图容器 + `LazyViews`）→ `_build_nav()` + 侧栏页脚 → `_nav_ready`。
3. **第三帧补低频件**：`finish_shell_extras()` = 顶栏右侧 → 解除 `_skip_first_run` 并 `view.sync_first_run()` 补新手引导卡 → `_extras_ready`。`main.py` 的 `_finish_startup` 顺序为：finish_shell → `update_idletasks` → `start_content` → 标内容就绪 → `root.after(1, _finish_extras)`。
4. 侧栏 9 行导航 `tk.Button` → `tk.Label` + `bind("<Button-1>")`，`_paint_nav_active` 同步兼容；`switch()` / `refresh_all()` 加 `self.views is None` 保护，占位期跳转不炸。
5. `ui_dashboard.refresh()` 开头判 `_skip_first_run`：引导卡 `grid_remove()` 而不是建卡，`sync_first_run()` 公开化供第三帧调。

### 3. 两个反直觉结论（都实测过）

- **去掉过渡加载窗反而更慢**：试过"有库就直接建主窗"，`imports-ready` 从 550 降到 386（省 50–70ms），但 `window-shell-painted` 变成 655/682（原本 635/647），内容就绪 1215/1224（原本 1103/1137）。原因是过渡窗先把窗口与字体栈热身一遍。**已回退，加载页始终保留**（并顺手把它从 6 控件品牌卡缩成一行字）。
- **nav 行 Button→Label 对 nav 段几乎无收益**：改造前后 `content-start → shell-nav-built` 都是 200–220ms。瓶颈在 pack 布局与字体首次解析，不在控件类型。这项保留（少一批选项初始化），但不计入收益。
- **字体档位数决定首帧成本**（Windows 真机控件探针 `_probe.py`）：同一 `(family,size,weight)` 首次建 Label 要 8.8–14.1ms，第二次同档仅 0.97ms；不设 `font` 的 Label 0.61ms，Entry 0.71，Button 0.99，Treeview 3.04，Scrollbar 1.62，Canvas 0.21。这解释了"少建同档控件几乎不省时间、少一档字体立省十几毫秒"，也是把加载页压到一行字、顶栏分两批的直接依据。

### 4. 包体：把从没用过的 numpy 拿掉

查 `dist/_internal` 发现 `numpy.libs` 20.2MB + `numpy` 6.1MB + `PIL` 10.7MB。全仓库只有 `filetools.py`、`thumbs.py`、`ui_files.py`、`tests/selftest.py` 四处 `from PIL import Image`，**全部在函数内延迟 import**，numpy 从未被代码 import——纯属 PIL 的 hook 带进来。两个打包脚本加 `EXCLUDES = ["numpy", "numpy.libs", "scipy", "pandas", "matplotlib"]` 与 `--exclude-module`：

| 产物 | 0.28.0 | 0.28.1 |
| --- | --- | --- |
| 便携目录 | 77 文件 / 71,639,812 字节 | **36 文件 / 41,300,944 字节** |
| 便携 zip | 33,022,547 字节 | **21,217,941 字节** |
| 单文件 exe | 32,392,545 字节 | **20,842,874 字节** |

PIL 完整保留（`_internal/PIL` 11,247,104 字节）。为确认功能没塌，用 `sys.modules["numpy"] = None` 造了一个"没有 numpy"的解释器跑图片转换：`convert_plan` → `convert_apply`，PNG→WEBP 返回 `{'ok': 1, 'failed': []}`。

### 6. 结论口径

- 中位 **0.83s / 1.42s**，双双进入 1 秒 / 1.5 秒区间，比 0.27.2 基线快 149ms / 98ms，比 0.28.0 快 575ms / 701ms。
- 但 6 次里各有 1 次没进区间（窗口 1036.8ms、内容 1668.8ms）。门禁若按"每次都有数据、每次都在阈值内"判，本版记 **"中位达标、个别次数未达标"**。不许写成"1 秒开机""全部达标"。
- 单文件版解包成本仍在（2.07–3.48s），不属门禁对象（门禁只测便携目录版）。
- 打包比源码多出的 ~180ms 主要是 PyInstaller 引导与安全软件首次扫描，这部分不在这版优化范围内。

## 六、边界与不能说的数字

- **1 秒目标只在中位数上达成**（829.0ms），6 次里仍有 1 次 1036.8ms。任何文档、Release 正文、落地页都不能写"已达标""1 秒开机"，只能写"中位 0.83s / 1.42s，个别次数未进区间"。
- 云主机这套 Tk 字体栈有一处明确的性能特征：**给控件显式设 `font` 时，每个控件约 9ms；不设 `font` 约 0.2ms**（同一进程内 A/B、`font=` 与 `configure(font=…)`、元组与命名 `Font` 对象都复现）。这让 Linux 上的"按控件计时"严重失真，不能直接当成 Windows 数字，也不能据此推到"排版导致慢"的结论。Windows 上的对应现象是"同一字体档位首次解析 8.8–14.1ms，第二次 0.97ms"（见第五节第 3 条），两者同源：成本落在字体解析与布局热身，不在控件个数本身。
- 因此量化收益一律以 Windows 重打包后的 `tests/perf_portable.py` 为准，云主机数字只作结构性参考。

## 七、下一步的杠杆（0.28.1 之后）

已经消化的：顶栏 275→51、首帧绘制 163→86、内容 392→288、包体 −30MB。

剩下三块，按性价比排：

1. **内容区 288ms**（`shell-content-built → content-ready`）：其中看板首建占大头（647→1136 里有 ~450ms 落在 `dashboard-built` + `dashboard-refreshed`）。下一步可把类别分布 6 行、近期动态 4 行的文字与横条改用一张 Canvas 一次绘制，省掉 Row 级控件树；也可让看板先出标题与合计，明细行再补一帧。
2. **第三帧 extras 约 280ms**（1137→1418）：搜索框、提醒、身份卡、新手引导卡。目前不影响主内容，但如果有用户抱怨"右上角按钮晚到"，可把提醒按钮的 badge 改成先占位后填数。
3. **0.46–0.5s 的解释器 + Tk 热身是硬底**，打包层只能靠继续缩包（当前 41MB 里 PIL 11MB、Tcl/Tk 若干）。真正突破 1 秒要靠"启动即显示、内容流式长出来"，也就是这版已经走的方向，边际收益会越来越小——**再往下压的期望值应放在 50–100ms 量级，不要预期再砍 300ms。**
